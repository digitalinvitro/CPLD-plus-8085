# beta/gfxstream — GFXSTREAM: непрерывный графический поток по UART 1М

> Подпроект линии `beta/txuart`: плата (8085 + XC95108) льёт анимацию 160×100 в
> ПК через аппаратный передатчик UART, ПК рисует её в окне WinForms.
> Текущее состояние: **прошивка v2.2 + вьюер v1.5** (статус 11-12-1).
> Живая спецификация протокола и статусы приёмки — [SPEC.md](SPEC.md);
> журнал решений и уроки — [../DEVLOG.md](../DEVLOG.md).

---

## 1. Цели и задачи подпроекта

**Цель.** Доказать и принять на железе непрерывный графический поток
плата → ПК по UART 1 000 000 бод: ноль потерянных байтов, стабильный
каденс на дисплее ПК, полоса, близкая к потолку архитектуры. Демо-экран —
наглядная приёмка всей TX-линии (CPLD-ядро TXUART + контракт CPU + канал
CH340G + клиент ПК).

**Задачи (все закрыты на v2.2):**

1. **Формат провода v1** — конверт `A5 5A [TYPE] [N_LO] [N_HI] [SEQ] [payload]`,
   TYPE 01 (полный кадр 2000 Б) / TYPE 02 (дельта 202 Б). Формат заморожен:
   все версии прошивки с v1 совместимы с вьюером без правок парсера.
2. **Демо-сцены** — быстрый шар (дельты), дитер-волна (полный темп),
   бегущая строка (шрифт, скроллинг) — три разных профиля нагрузки.
3. **Калибровка периода** — согласование темпа потока с сеткой дисплея ПК
   (v2.1: период = 3 тика WM_TIMER; v2.2: калибровка по живому логу,
   реальный период платы 46.874 мс = ровно 3 тика). УРОК 13: темп провода
   должен быть кратен сетке дисплея — иначе дискретные объекты «прыгают».
4. **Диагностика на обеих сторонах** — CSV-телеметрия вьюера (`-Log`),
   форензик-анализатор логов (`gfx_log_analyze.py`), счётчики краски/флешей
   в статусе вьюера v1.5.
5. **Потолок полосы** — TXSTRESS-кампания (см. `../txuart/README.md`):
   измеренный максимум линии и архитектурный пол задокументированы (§6).

## 3. Формат провода (v1, заморожен)

```
A5 5A [TYPE] [N_LO] [N_HI] [SEQ] [payload ...] [FFh-добивка до 2006 Б]
```

- Заголовок 6 Б: преамбула `A5 5A`, тип, длина payload (LE), SEQ (mod 256).
- **TYPE 01** — полный кадр: `N = 07D0h` (2000 Б = 100 строк × 20 Б).
- **TYPE 02** — дельта: `N = 00CAh` (202) = маска 13 Б + 9 × [номер строки][20 Б].
- Хвост конверта добивается `FFh` до **ровно 2006 Б** (UART-idle: парсер ПК
  пропускает FF-серии, ресинк — по преамбуле `A5 5A`).
- Каждый кадр занимает на проводе одинаково 2006 Б ⇒ физический темп
  константен (§6), SEQ монотонно растёт, потеря кадра видна как разрыв SEQ.

## 4. Организация экрана

- **160×100 пикселей, 1 бит/пиксель** (ч/б), MSB = левый пиксель.
- Кадр = **100 строк × 20 байт** (160/8); полный кадр payload = 2000 Б.
- Фон демо — сетка 8×8: строка кратна 8 или последняя (99) → байт `FFh`,
  иначе `80h`; последний байт каждой строки `| 01h` (рамка по краям).
- **Шар**: 8 px × 7 строк, сплошной `FFh`; поле 20 клеток × 93 строки
  (col 0..19, row 0..92, чётные).
- **Дизеринг**: 16 уровней плотности из таблицы `DIT` (000h → FFh) —
  серая шкала средствами 1 bpp.
- **Бегущая строка**: полоса строк 46..53 (8 строк), шрифт 8×8 (23 глифа),
  битмап 48 символов × 8 строк в ОЗУ, окно 20 байт на строку.

## 5. Прошивка gfxstream_v22 — принципы работы

### 5.1 Память и порты

ROM 0000h..7FFFh (код + таблицы: `TBL`, `DIT`, `NEG16`, `MMASK`, `FONT`,
строка баннера), ОЗУ 8000h..FFFFh (32 КБ):

| Адрес | Размер | Назначение |
| --- | --- | --- |
| `9800h..981Ch` | 29 Б | `STATE`: SEQ, счётчик кейфреймов, шар (col/row/шаги), сцена, счётчики сцены, заголовки `S_HDRF`/`S_HDRD` (9811h/9817h, по 6 Б) |
| `9900h..990Ch` | 13 Б | `MSKBF` — маска дельты шара (строится на кадр) |
| `A000h..A17Fh` | 384 Б | `MWORK` — битмап бегущей строки 8×48 |
| `A200h..A27Fh` | 384 Б | `MMASR` — мастер-копия битмапа |
| `FFF8h` | — | SP (стек вниз) |

Итого ОЗУ ≈ 1.4 КБ (~4%). Кадровый буфер (FB) **не используется**:
каждый кадр строится аналитически и льётся в UART прямо из регистров —
генерация и посылка слиты (fusion). Порты: **OUT 04h** — данные TX,
**IN 05h бит 1** — TXRDY (в прошивке не опрашивается: слепой ритм надёжнее,
см. §7).

### 5.2 Кадр, пути, тайминг, калибровка

- Кадр = голова (заголовок) + payload + **пад пути** `P_*` + **единый
  ожидатель** `WTAIL` (цикл 24T × `W_V2` + NOP-хвост). Работы путей
  выровнены падами так, что **каждый путь занимает ровно один период**.
- Пады: `P_H` 46 (выравнивание голов перед маской дельты), `P_BF` 1,
  `P_BD` 1052, `P_DI` 760, `P_MF` 183, `P_MD` 496; `W_V2` = 2262.
- **Период кадра (v2.2, калибровка по живому логу владельца):**
  реальный период платы оказался 46.3481 мс = −1.124% от номинала
  146 484T (сим считает такты по таблице 8085, силикон исполняет смесь
  инструкций быстрее; пад-петля 24T нейтральна для обеих архитектур).
  Коррекция — добавка пада **+1644T** (`W_V2` 2194→2262, +3 NOP в хвосте):
  **реальный период 46.874 мс = ровно 3 тика WM_TIMER 15.625 мс = 21.333 FPS**.
  В симуляторе период 148 128T = 47.401 мс — сим-такты ≠ реальным
  (УРОК 15: абсолютный период сверяется только по живому логу, обёртки SEQ).
- Исключение (документировано): кадры входа в сцену несут switch (~250T),
  вход в S2 — ещё и копию битмапа мастер→работа (16.9kT); ≤1 кадра на цикл,
  поглощается дисплеем.
- После POR ~503 мс плата выдаёт баннер `GFXSTREAM v2.2` (CR/LF), затем
  непрерывный поток кадров.

### 5.3 Сцены (цикл 910 кадров ≈ 42.7 с)

| Сцена | Кадров | Типы | Содержание |
| --- | --- | --- | --- |
| S0 БЫСТРЫЙ ШАР | 250 | дельты TYPE 02; кейфрейм TYPE 01 на входе и каждый 100-й | шар 8×7 px, шаг ±2 клетки (16 px) / ±2 строки, отскок flip-recompute; дельта = ровно 9 строк `[RMIN..RMIN+8]` ⇒ N=202 сохранён; 341 px/s |
| S1 ДИТЕР-ВОЛНА | 240 | все TYPE 01 (полный темп) | байт строки `DIT[(row + NEG16[t&15]) & 15]`, 16-ступенчатый «занавес», волна вниз 1 строка/кадр |
| S2 БЕГУЩАЯ СТРОКА | 420 | вход TYPE 01, далее дельты строк 45..53 (фиксированная маска `MMASK` E0h/3Fh) | битмап 48 симв. («GFXSTREAM V2 - 160X100 - …» — текст унаследован от v2), сдвиг влево 1 px/кадр RAR-цепочкой по убыванию адресов (УРОК 11); 21.3 px/s |

В цикле 910 кадров: 244 полных + 666 дельт. Смена сцены всегда начинается
с полного кадра (ресинк-точка для вьюера).

### 5.4 Сборка и проверка

- Сборка: `python3 beta/txuart/rom/txstress/asm8085.py gfxstream_v22.asm gfxstream_v22`
  (ассемблер asm8085, CP1251; есть UTF-8 контроль round-trip).
- Проверка: `python3 beta/txuart/scripts/sim_gfxstream_v2.py` — исполнение
  **реального hex** + эталонная модель сцен: побайтовая сверка, SEQ без
  пропусков, периоды путей, мин-гэп ≥32T, 0 отбросов TX. v2.2: 940 кадров
  «ВСЁ ОК».

## 6. Полоса пропускания

Линия: 1 000 000 бод 8N1 ⇒ **100 000 Б/с** полезной ёмкости; байт 8N1 =
10 мкс = **31.25T** (T = 320 нс @ 3.125 МГц).

| Поток | На проводе | Темп | % линии |
| --- | --- | --- | --- |
| Конверт кадра (любой тип, с FF-добивкой) | 2006 Б | 42 795 Б/с ≈ **42.8 КБ/с** | **42.8%** |
| Полезный payload TYPE 01 | 2000 Б | 42 795 Б/с | 42.8% |
| Полезный payload TYPE 02 | 202 Б | 4 309 Б/с | 4.3% |
| Средняя полезная за цикл 910 кадров | — | ≈14 600 Б/с | ≈14.6% |

Демо сознательно не насыщает линию: запас канала ~2× оставлен под будущие
эффекты. Измеренные пределы (линия `beta/txuart`, TXSTRESS):

- **69 770 Б/с = 69.8% линии** — честный средний темп TXSTRESS v11
  (цикл 42T со «страховочным» двойным OUT, TX_BOTH=1), 60-с прогон,
  52/52 цикла, 0 ошибок;
- **пол архитектуры = 32T/байт = 97 656 Б/с (97.7%)** — вариант p04,
  железно подтверждён (97 887 Б/с = 97.9%); выше — только CPLD FIFO/пейсинг,
  который не влезает в XC95108 (фит v2.3 103/108 МЦ);
- бод >1М бессмысленен: лимит — CPU (темп записи 32T не зависит от бода).

## 7. Подпрограммы выгрузки области памяти в UART (ассемблер)

Контракт TX-ядра: **запись в занятый передатчик отбрасывается** (RTL).
Поэтому каждый посылающий цикл прошивки выдерживает шаг **≥ 31.25T/байт**
— тогда запись никогда не попадает в busy, и ноль отбросов гарантирован
по построению (доказано TXSTRESS и SPRINT-фазой на железе). В gfxstream_v22
три посылающих цикла:

**(а) Поток из регистров — 32T/байт** (минимальный шаг, генерация слита
с посылкой; так идут сетка/шар/дизер):

```asm
; D = счётчик байтов, A = байт кадра
BP1:    OUT TXPORT        ; 10T — байт в TX (порт 04h)
        NOP               ;  4T
        NOP               ;  4T
        DCR D             ;  4T
        JNZ BP1           ; 10T   ->  32T/байт >= 31.25T
```

**(б) Блок из ОЗУ через LDAX — 37T/байт** (заголовок конверта `S_HDRF`/
`S_HDRD`, маска дельты `MSKBF`/`MMASK`):

```asm
        LXI D,S_HDRF      ; DE -> блок в ОЗУ
        MVI C,006h        ; длина: 6 байт заголовка
BHD:    LDAX D            ;  7T — байт из ОЗУ
        OUT TXPORT        ; 10T
        INX D             ;  6T
        DCR C             ;  4T
        JNZ BHD           ; 10T   ->  37T/байт >= 31.25T
```

**(в) Линейная выгрузка области памяти (HL) — 37T/байт** (строки битмапа
бегущей строки из `MWORK`, баннер из ROM):

```asm
        LXI H,MWORK       ; HL -> битмап строки (ОЗУ A000h)
        MVI E,008h        ; 8 строк полосы
MBL:    MVI C,014h        ; 20 байт окна строки (160 px)
MBLA:   MOV A,M           ;  7T — байт из ОЗУ
        OUT TXPORT        ; 10T
        INX H             ;  6T
        DCR C             ;  4T
        JNZ MBLA          ; 10T   ->  37T/байт >= 31.25T
        INX H  (x28)      ; окно -> следующая строка битмапа (48 Б/строка; DE занята)
        DCR E
        JNZ MBL
```

Все три цикла — линейные (без CALL): цена байта постоянна и видна в
листинге, что и позволяет держать период кадра с точностью до такта.
Опрос TXRDY (`IN 05h`, ≥24T/байт) дороже слепого 32T-ритма и потому
не применяется.

## 8. Железо под gfxstream: top_txuart_por6_v23.v

Файл `beta/txuart/top_txuart_por6_v23.v` (рабочий — CP1251, рядом `_utf8`
близнец) — top-модуль платы **retro PC (8085 + XC95108) + аппаратный
передатчик TXUART**, база = lowsize `v3.9.8-clear` ред.2 (бит-в-бит:
узел тактирования, POR-цепь, харденинг сброса, FSM шины).

- **Цель и ресурс**: XC95108-15PQ100C. Фит v2.3 (11-9 7:26PM, SUCCESSFUL):
  **103/108 МЦ (95%), 339/540 ПТ, 211/216 вх.ФБ (98%), 77 триггеров,
  72/81 нога**.
- **Тактирование**: вход CPLD 25 МГц (**H1 с шунтом — ОБЯЗАТЕЛЕН**),
  кольцо one-hot `s0..s3` на clk 25 МГц; `X1 = s0` (duty 1/4, 6.25 МГц) —
  такт CPU-логики → **CPU 3.125 МГц**, `X2 = ~s0`. Вся логика (включая
  TXUART и POR-цепь) живёт в одном домене clk 25 МГц; сброс логики — через
  сеть GSR от узла `cpu_rst`; `CS_n` от FSM шины.
- **TXUART-ядро** (~18 МЦ, механика txclient v8 / hwuart v4.0.1): сдвиговый
  регистр self-idle, jam-фазировка, регистровый строб `ld_tx_q`; формат
  8N1; **запись при busy отбрасывается** — отсюда контракт ≥32T/байт (§7).
- **v2.3 (ключевое изменение линии)**: бод понижен с 1 562 500 до
  **ровно 1 000 000** = 25 МГц/25 (baud_cnt расширен 4→5 бит, +1 МЦ).
  Причина — первый железный прогон v2.2: сетка CH340G не содержит
  1 562 500, драйвер **молча** ставил 1 500 000 (+4.17%) → старший бит
  каждого ~второго байта читался как стоп-«1» (терминал показывал мусор).
  1 000 000 делит нацело сетку любого моста (12/24/30/48 МГц).
- **Приёмка железа**: терминал 1 000 000 8N1 — чистая строка
  «TXUART v2.2 OK N=87…98»; затем TXSTRESS-кампания (§6) — 52/52 цикла,
  0 ошибок.
- Порты со стороны CPU: **OUT 04h** — данные TX, **IN 05h бит 1** — TXRDY
  (биты 0/1 = TX idle), `05h` же — алиас «страховочного» второго OUT
  (TX_BOTH в TXSTRESS).
- Сопровождение: тестбенчи `tb_txuart_v1/v2/v21/v22/v23.v`, симы
  `scripts/sim_txuart_v*.py`, ноги — `top_txuart.ucf`, архивы фитов —
  `retro_pcld_top (txuart-fit*.rpt)`.

## 9. Вьюер gfx_view.ps1 — запуск из командной строки

Требования: Windows PowerShell 5.1+ или pwsh 7 (файл UTF-8 **с BOM**),
.NET WinForms; COM-порт свободен (терминал и прочие потребители закрыты);
в ПЗУ платы — `gfxstream_v22.hex`.

```powershell
# обычный сеанс (порт по умолчанию COM13, бод 1 000 000, масштаб 3):
.\gfx_view.ps1 -Port COM13

# сеанс с телеметрией (обязателен для приёмки; CSV v1.5: kind D/P/F):
.\gfx_view.ps1 -Port COM13 -Log log2.csv

# самопроверка без порта (12/12 проверок на синтетическом потоке):
.\gfx_view.ps1 -SelfTest

# из cmd.exe:
powershell -ExecutionPolicy Bypass -File .\gfx_view.ps1 -Port COM13 -Log log2.csv
```

Параметры: `-Port` (по умолч. COM13), `-Baud` (1000000), `-Scale` (3 —
окно 480×300), `-Log <файл.csv>`, `-SelfTest`.

Что даёт v1.5 (диагностика встроена): таймер 2 мс + `timeBeginPeriod(1)`
(тик реально ~2 мс), **краска сразу в тике декода** (гейт 36 мс удалён —
интервал краски = интервал провода ±2 мс), сброс стартового бэклога >3000 Б
(DiscardInBuffer + ресинк, счётчик «флеш»), CSV с колонкой `kind`
(D=декод, P=краска — seq покрашенного, dt, пропуски; F=флеш), статус с
«краска ср/макс + пропуск + флеш», сводка при закрытии окна. Логи v1.4
остаются читаемыми (анализатор различает по шапке).

## 10. Приёмка v2.2 — критерии и инструмент

Прошить `gfxstream_v22.hex`, взять **новый** `gfx_view.ps1` (v1.5), сеанс
`-Log log2.csv` ≥ 2 мин, лог прислать. Вердикт выдаёт анализатор:

```bash
python3 beta/txuart/scripts/gfx_log_analyze.py log2.csv
```

Критерии ПРИНЯТО: обёртки SEQ = 12.000 с ± 0.3%; интервал краски
47 ± 3 мс ровно (p90−p10 ≤ 6 мс); пропуски краски 0; разрывы SEQ 0;
флеши ≤ 2 и только на старте. Фон форензики v2.2: провод цел (0 разрывов
SEQ на 2606 кадрах), источник рывков v2.1 — скользящая фаза кадра по сетке
WM_TIMER (−1.124% периода платы) и гейт v1.4 (3.37% структурных пропусков
краски) — устранены калибровкой и вьюером v1.5 (УРОК 14: краска не должна
жить на сетке WM_TIMER).
