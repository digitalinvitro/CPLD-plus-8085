# beta/lowsize — линия СНИЖЕНИЯ количества ресурсов CPLD

Папка для работ над **уменьшением размера HDL-дизайна в CPLD** (число МЦ /
ПТ / входов ФБ по фиту) при неизменной функциональности и неизменной
производственной частоте **CPU 3,571 МГц** (X1/X2 = 7,143 МГц, кольцо N=7,
терминал 6857 8N1).

## Решение владельца по подтяжкам CS1/READY (фиксация, clk10-64)

Соединение CE2 ОЗУ (P99 → CS1) и READY (P87 → CPU) — **внутри CPLD
дизайном, БЕЗ пайки**. Вариант «внешние подтяжки резисторами + свободные
МЦ» отклонён. Проверено по фиту v3.9 10-29 8:45PM (retro_pcld_top (v39).rpt):

- `CS1` — **FB2_3, нога 99: 0 ПТ, 0 входов ФБ** (`CS1 <= '1'` в Equations);
- `READY` — **FB4_5, нога 87: 0 ПТ, 0 входов ФБ** (`READY <= '1'`).

Итого дизайн-внутреннее соединение стоит **ровно 2 МЦ** — и это самые
дешёвые МЦ дизайна (ни одного птерма, ни одного входа ФБ, логики нет).
В v3.9.2 и дальше CS1/READY остаются константами '1' в RTL без изменений.

## Принципы линии lowsize

1. Частота CPU, тайминги шины (T = 280 нс, /WE 80 нс, t_AS 40 нс), POR
   (1120 нс, запас 1,33x) и терминал 6857 8N1 — НЕИЗМЕННЫ. Меняется только
   реализация.
2. Каждая версия — полный комплект: RTL CP1251 (+UTF8-копия), генератор
   из предыдущей версии, симуляция эквивалентности/узла, шапка с чек-листом
   фита, обновление этого README.
3. Верификация ДО фита: дифсимуляция двух RTL (новый vs предыдущий) на
   общем стимуле — расхождение выходов 0; для узла тактирования — ещё и
   побитовая эквивалентность X1/X2/por старой реализации.
4. Фит владельца в ISE → .rpt на аудит → только потом .jed.

## v3.9.2 (clk10-65, 2026-10-30): кольцо one-hot N=7 → двоичный счётчик mod-7

Первая версия линии lowsize после базы v3.9.1. Мотивация по фиту v3.9
(10-29 8:45PM): 88/108 МЦ, входы ФБ 202/216, узел тактирования = 8
триггеров (r0..r6 + x1_n). Кольцо в v3.8 выбрали ради входной ренты
(декоды равенства ели входы двух ФБ), но МЦ-бюджет оно платит сполна:
7 триггеров состояния. Двоичный mod-7 хранит то же состояние в 3:

- `cnt[2:0]`: двоичный 0..6, wrap по декоду cnt==6, INIT=000; нелегальное
  111 недостижимо, при внешнем попадании восстанавливается за 1 фронт
  (7+1 = переполнение 3 бит → 000);
- фаза X1 — **комбинационная**: `X1 = (cnt != 0) ^ x1_n` — точный
  эквивалент `(~r0) ^ x1_n` кольца (состояние k кольца <=> cnt==k,
  включая INIT r0=1 <=> cnt=0); узор «1111100» (100/40 нс), X2 = `~X1`
  точно, фронты ровно 140 нс, CLK CPU 280 нс 50/50 — **бит-в-бит v3.9**;
- `x1_n`: set cnt==3 / clear cnt==4 (NEGEDGE) — те же фазы, что r3/r4
  кольца, импульс 40 нс;
- `por_ce = (cnt==1) | (cnt==6)` — те же состояния, что r1|r6: интервалы
  200/80 нс, POR = 1120 нс бит-в-бит v3.9 (пара {0,1} дала бы POR 2240 нс
  — забраковано по требованию эквивалентности).

Цена: декоды равенства вернулись в узел (класс п.9 — фиттер трижды терял
полярность декодов в фятах 10-22); теперь они 3-битные и дешёвые,
чек-лист h) в шапке RTL требует сверку уравнений по таблице истинности.
Ядра X1/X2 выросли 2 → 4 ПТ. Экономия: **−4 МЦ** (8 → 4 триггера узла;
прогноз 88 → 84/108, 85 если фиттер выделит por_ce в хелпер-МЦ).

Верификация (обе ступени ПАСС, до фита):
1. **Дифсимуляция двух RTL** (scripts/tb_v392_diff.v + run_tb_v392.sh,
   Icarus Verilog 12.0): v3.9.1 (эталон) и v3.9.2 в одном тестбенче,
   общий стимул, сравнение всех 18 выходов/шин каждые 5 нс: направленные
   сценарии (POR, шина чтения/записи/writeback, порты, клавиатура, TX
   v3.7, ALE-глюки, cpu_rst в каждой фазе) + рандом 4 сида = 10 595
   циклов, 4078 импульсов /WE: **0 расхождений**, логи виртуальных ОЗУ
   идентичны 4077/4077, спеков 0 (/WE ровно 80 нс, t_AS ≥ 40 нс).
2. **Узловая симуляция** (scripts/sim_v392_div7.py): точная семантика
   RTL, счётчик против модели кольца: 15/15 ПАСС — бит-в-бит X1/X2/
   por_ce/por_run на 200 мкс; узор «1111100»; rising/falling фронты
   ровно через 140 нс; duty-интервалы 100/40 нс; por_ce {10,4} полутакта
   (200/80), среднее ровно 140 нс; POR 1140 нс ≥ нормы 840 (запас
   1,33x); перебор 8 состояний cnt (111 → 000 за 1 фронт, узор ==
   кольцу); регрессия эталона — 128 состояний кольца → one-hot за
   ≤ 3 posedge.

## v3.9.3 (2026-11-02): сброс логики → сеть GSR

Директива владельца после разбора «проблемы сброса» по трём фита́м линии
(v3.9 / v3.9.1 / v3.9.2): мера по сбросу направлена на снижение размера
прошивки — отрабатывать её по линии lowsize, в более новой прошивке.

Что было (v3.9 → v3.9.2, Task 25): пин RST (SW20) физически стоит на
выводе I/O/GSR (P1), но **сеть GSR не использовалась** — все три .rpt
фиксируют «Global set/reset net(s) unused», «GSR : 0». Сброс был
**синхронным через D-gating**: `cpu_rst = RST | por_run` входил
литералами в D-функции всех триггеров логики. Цена по фита́м:

| Фит | вх. ФБ | литералы сброса | защиты NOT RST / NOT por_run / OR (RST) |
|-----|--------|-----------------|------------------------------------------|
| v3.9 (10-29) | 202/216 | RST+por_run во всех 6 ФБ = 12 (5,9%) | 57 / 42 / 2 |
| v3.9.1 (10-30) | 186/216 | те же 12 (6,5%) | без изменений |
| v3.9.2 (10-30) | 180/216 | те же 12 (6,7%) | 70 / 55 / 3 |

Что стало (п.18 шапки RTL):

- триггеры логики (state, rd_seen, wr_seen, addr_latch, bus_reg, seg_q,
  dig_q, snd_q, kbcol_q) описаны **асинхронно** (`posedge clk or
  posedge RST, if (RST)`) → фиттер сводит общий асинхронный сброс на
  **сеть GSR**: минус ~2 входа в большинстве ФБ (прогноз 180 → ~168-172),
  минус литералы сброса в D-функциях (ПТ 209 → ~190-205);
- **вне домена GSR** (бит-в-бит v3.9.2): делитель cnt/x1_n (X1 не
  глушится, фаза CLKOUT не прыгает), por_sh/por_run (POR только по
  питанию, INIT=FF/1), sod_q, tx_pass/tx_q (async SR по cpu_rst —
  cpu_rst держит tx_pass=0 весь POR: враждебный SOD в окне POR не
  «захватывает» TX), `RESET_IN = ~(RST \| por_run)` — без изменений;
- **защита окна POR**: FSM в окне por_run=1 живой (GSR не активен), а
  шина CPU в сбросе «floated» (ВМ85А: управления/адрес/данные в 3-м
  состоянии) → вход в writeback гейтится (`!por_run` в S_T2) — /WE в
  окне POR невозможен по построению;
- поведение: сброс логики стал асинхронным (фиксация значений в момент
  нажатия, снятие в момент отпускания; v3.9.2 — на такт позже);
  нормальные циклы бит-в-бит v3.9.2.

Верификация (обе ступени ПАСС, до фита):
1. **Дифсимуляция двух RTL** (scripts/tb_v393_diff.v + run_tb_v393.sh,
   Icarus 12.0): v3.9.2 (эталон) vs v3.9.3, общий стимул, все выходы/шины
   каждые 5 нс; НОВОЕ: окно асинхронного сброса (±45 нс вокруг кнопки —
   ожидаемое свойство меры), **враждебные «плавания» шины в окне POR**
   (имитация floated-линий ВМ85А, 27 тактов), spec «/WE никогда не низок
   при RESET_IN=0» для обеих версий, записи-«тени» (аборты /WE в окне

   **0 расхождений, 0 спеков, не-тени логов идентичны**.
2. **Узловая симуляция** (scripts/sim_v393_gsr.py): 9/9 ПАСС — POR 1140 нс

## v3.9.5 (2026-11-05): GSR-источник = cpu_rst — исправление дефекта старта v3.9.3/v3.9.4

встречает CPU на выходе из сброса ГРЯЗНОЙ. Класс-эффекты на старте:
rd_drive=1 → контеншн CPLD против '573 на A-сетях; мусорные декоды
портов. Кнопка сброса не спасает (снятие GSR снова оставляет FSM на
плавающей шине), передёргивание питания перебрасывает «лотерею»
порогов плавающих линий — отсюда «рано или поздно запускается» и
разброс по платам. Гейт `!por_run` (добавлен в v3.9.3) закрыл только
заход в writeback — и держит его честно (WE_n=0 в POR: 0 нарушений),
но весь остальной блуд он не закрывает.

**Доказательство (fuzz-тест, `scripts/tb_por_fuzz.v` +
`run_tb_por_fuzz.sh`, Icarus 12.0, 100 сидов)** — модель «плавающей»
шины: случайные переключения ALE/RDn/WRn/IOM/A15/A/D каждые 10 нс
в окне POR + 200 нс хвост («лотерея порогов» по сидам):

| Метрика | v3.9.2 | v3.9.4 (дефект) | v3.9.5 (фикс) |
|---------|--------|------------------|----------------|
| грязь в момент снятия por_run | **0/100** | **100/100** | **0/100** |
| rd_drive в окне POR (тактов с контеншном A) | 0 | 86 | 0 |
| WE_n=0 в окне POR (нарушение gate) | 0 | 0 | 0 |
| «грязь на старте CPU» (+200 нс хвост) | 84/100 | 100/100 | 94/100 |

Хвост (+200 нс после снятия por_run) — общий для ВСЕХ линий (cpu_rst
снят и в v3.9.2: 84/100!) и в поле не убивает старт (v3.9.2 стабильна:
первый реальный цикл CPU вымывает свежий мусор); смерть старта — это
входить в хвост ГРЯЗНОЙ и ГЛУБОКО (порты/шины, накопленные за весь
POR), чем v3.9.3/v3.9.4 и отличаются.

**Фикс (мера п.20):** `always @(posedge clk or posedge cpu_rst) begin
if (cpu_rst) ...` — условие v3.9.2 на асинхронной структуре v3.9.3.
GSR-сеть теперь запускается от узла cpu_rst (RST|por_run): в окне POR
логика прикована АСИНХРОННО с t=0 (por_run INIT=1 → GSR=1 ещё до
первого фронта), кнопка — прежняя (RST=1 → GSR=1), POR-цепь/делитель/
sod_q — по-прежнему ВНЕ GSR (por_run сам себя сбрасывать не должен),
гейт `!por_run` в S_T2 остаётся вторым рубежом, tx_pass/tx_q (async SR
по cpu_rst) — без правок. Дельта RTL — 2 слова (генератор
`scripts/gen_v395.py` контролирует её автоматически).

Верификация фикса: (1) fuzz — таблица выше, v3.9.5 = 0/100 грязи,
0 контеншна; (2) дифсим v3.9.4 vs v3.9.5 (`scripts/tb_v395_diff.v` +
`run_tb_v395.sh`): **10 595 циклов, 0 расхождений выходов/шин, 0
spec-нарушений, логи ОЗУ идентичны (4077/тени 50=50), RST-окна
строгие** (поведение сброса у обеих идентично: при por_run=0 условие
cpu_rst ≡ RST); окно сравнения закрыто до конца блока враждебных
«плаваний» (1200 нс, ресинхронизация) — в «плаваниях» траектории
ЗАКОННО расходятся (v3.9.4 входит с «стартовым преимуществом»
бродяжничества, v3.9.5 — чистым из IDLE): это и есть тот мусор,
который убирает фикс, свойство меры, не дефект; T0 POR: 4 сдвига,
≥840 нс, повторного POR нет. (3) RTL-дельта = ровно 2 строки
(контроль в gen_v395.py), round-trip CP1251.

Экономика (прогноз фита): источник GSR = узел cpu_rst вместо ноги RST
напрямую — +1 ПТ (OR) в ФБ гейта RESET_IN (RST и por_run уже
импортированы туда), вх.ФБ +0..2; ожидание ~82-84/108 МЦ, ~180-190
ПТ, ~168-172 вх.ФБ. ЕСЛИ фиттер не сведёт узел на GSR (fallback —
PT-сбросы на каждом триггере) — функционально корректно, дороже по
ПТ/вх (анатомия v3.9.2: ~12 вх.ФБ импортов) — .rpt на разбор в обоих
случаях. **Следствие для линий-наследников: тот же класс дефекта
живёт в beta/hwuart (v4.0.0/v4.0.1 — та же GSR-мера в базе) и
beta/txclient (v7/v8) — в hwuart нужен v4.0.2 с теми же 2 строками;
.jed v4.0.1 не шить даже после успешного фита.**

## rom/ — МОНИТОР fw_mon: дисплей + клавиатура, меню ACDE (клк10-69/70)

Штатный монитор платы (прошивается в flash A29040B с offset 0; тест-
прошивки выше после приёмки 10-30 больше не нужны). По ТЗ владельца:
меню — 4 буквы на 4 разрядах **«ACDE»** (клк10-70: C вместо посаженной
раньше на B клавиши «P» — C созвучно с Code и физически есть на матрице
0__2; B снова обычная тетрада; добавлен режим D).
**Инструкция пользователя с примерами: [manuals/fw_mon_acde_manual.md](../../manuals/fw_mon_acde_manual.md)** · PDF в ретро-стиле (с рисунками 7-сегментного индикатора к командам): [manuals/fw_mon_acde_manual_retro.pdf](../../manuals/fw_mon_acde_manual_retro.pdf).
**F1 (4__1) — системное меню «ACDE»** (из любого режима);
**A (0__0) — ввод адреса** (4 тетрады, вдвигаются справа: 8 → «___8»,
80 → «__80», 5-я вытесняет старшую; Enter — запись);
**C (0__2) — ввод кода (Code)**: байт в кодах 8085 — 2 тетрады в правых
разрядах («__C3»), Enter — записать в [ADDR] и ADDR++, пустой Enter —
игнор, F1 — конец ввода, в меню;
**D (0__3) — просмотр кода с введённого адреса**: в правых разрядах байт
[ADDR] («__C3»), Enter — ADDR++ и следующий байт, F1 — в меню; режим
только чтение (тетрады игнорируются);
**E (1__3) — запуск с введённого адреса** (по умолчанию 8000h): гасит
дисплей, DI, регистры 0, SP=FFE8h, в стеке адрес возврата — выход из
пользовательской программы **RET (C9)** возвращает в «ACDE» (ждёт
отпускания клавиш + дебаунс), иначе RESET. В меню остальные клавиши
(0-9, B, F, F2, Enter) игнорируются; в режимах адреса/кода A–F —
тетрады. Короткий тик ~32 мс (~468 Гц) на каждое нажатие, дисплей при
тике НЕ гаснет (SND едет в записи DIGP). Регенерация с блэнкингом
«гашение → разряд → глиф» (клк10-67). Память: переменные монитора
FFE8h–FFF8h, стек с FFE7h вниз; пользовательская область 8000h–FFE7h;
запись в ROM (0000–7FFF) железо отбрасывает. Образ 933 байта
(0000h–03A4h).

Верификация ДО железа: `rom/verify_mon.py` (наследник verify_fw.py:
мини-8085 с точными T + DI/EI, модель портов/матрицы/дисплея, запись в
ROM отбрасывается) — **40/40 ПАСС**: boot-гашение «8.», меню ACDE, F1
глобально, ввод адреса посимвольно, Enter, ввод кода по C с записью в
ОЗУ и ADDR++, игнор пустого Enter, отброс записи в ROM, запуск E с
исполнением RET пользователя и возвратом в меню, просмотр D (байт,
Enter — следующий, тетрады игнорируются, F1 — в меню), B снова тетрада
(в меню — игнор), вытеснение 5-й тетрады, нет авто-повтора при
удержании, F2 игнорируется, карта клавиш (row,col)→клавиша, блэнкинг —
0 нарушений на 5007 фаз, тон 468 Гц, тик 32,1 мс (замер на FAST-образе,
единица 1069 мкс = 3818 T). Ранее (клк10-69) отловлены и исправлены
3 бага ДО железа: (1) DISPATCH затирал код клавиши чтением STATE (все
ветки сравнивали не клавишу); (2) счётчики циклов TICKON/дебаунса были
в HL, который портит новый 4-разрядный REFRESH (вечный тик); (3) пороги
показа тетрад адреса были инверсными. Ассемблер asm85.py: метка на
отдельной строке получает адрес 0000 — везде инструкция на одной строке
с меткой.
