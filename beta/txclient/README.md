# v3-логгер: сериальный захват hi-байта (текущий кандидат)

## Разбор фита v2 у владельца (retro_pcld_top.rpt, 11-1 9:26AM — Placement Failed)

- Ресурсы фита: **МЦ 90/108, ПТ 328/540 — запас есть; входы ФБ 216/216
  (100%) — все 6 ФБ по 36/36**. `ERROR:Cpld:891 — Cannot place signal
  shreg<4>. Too many function block inputs required`; 21 узел не размещён
  (`shreg<2,4,5,7>`, `addr_latch<0..6>`, `hlda_q`, `por_sh<3..7>`,
  `state_FSM_FFd2`, `bit_cnt<1>`…); 6×`WARNING:Cpld:896` в FB3 (буферы
  BUFR `D<5..1>`, `TX` — +6 МЦ).
- **Причина**: параллельная загрузка `ah_bus` в shreg (идея v2) требует
  входы `{A15, AH14..AH8}` **в каждый ФБ, где лежит триггер shreg** — а
  shreg расползается по 3–4 ФБ (в фите — FB2/FB4/FB6) = +8–9 входов × 3–4
  ФБ, плюс коллапс фитайтера: D-функции shreg по 25–29 входов (`shreg<6>`
  28, `shreg<3>` 29, `shreg<1>` 26). Итог — входы ФБ кончились.
- **⚠ UCF НЕ ПРИМЕНИЛСЯ**: в отчёте `HOLD … FB4_14, pin 95` — фиттер
  поставил HOLD на **P95** (на плате это земля флэш-A16!), а P81 (CPU.HOLD,
  нога 39) остался unused → «Ground on Unused IOs» заземлил бы его. Фит
  собран **без** `beta/txclient/top_txclient.ucf` (там `NET "HOLD"
  LOC="P81"`). Остальные ноги совпадают с картой. **Перефитовать только с
  txclient-UCF и сверять: HOLD = P81 со знаком `~`.** С .jed от этого фита
  txclient молчал бы вечно (HOLD прибит к земле), а на P95 дёргался бы
  hold_req (безвредно только потому, что /CE флэша при hold_req=1 гасится).
- План Б без правки RTL (если v3 не ляжет): в ISE Process Properties →
  Fit → **Collapsing Input Limit 36 → 20–24** (фитайтер сам просил в
  ERROR 891) — запрет коллапса вынесет загрузки `ah_bus` в хелпер-МЦ
  (запас 18 МЦ есть); применить к v2.

## Лекарство v3: hi-байт сдвигается с живых AH-пинов

Параллельная загрузка заменена **сериальной**: в фазе захвата (10 тиков
подряд) в `shreg<9>` через мультиплексор 8:1 заходят
`[старт=0, A8, A9, …, A15, стоп=1]`, при этом **весь shreg сдвигается
вправо каждый тик**. После 10-го тика кадр 1 лежит в shreg готовый —
старт-бит уже в `shreg[0]` — и TX сразу уходит в '0'. Мультиплексор нужен
**только `shreg<9>`** — **AH-пины входят ровно в 1 ФБ** вместо 3–4
(экономия ~16–24 вх. ФБ против v2 — провал устранён по построению).

Механика: `cap_run` (1 триггер) ставится тем же стробом, что и в v2
(`state==S_T2 && !WRn && !wr_seen && hold_req && TXB_IDLE`); счётчик фазы —
штатный `bit_cnt` (0..9, новых триггеров нет); во время фазы `case(tx_byte)`
не выполняется (защитный релиз IDLE недостижим); `TX = shreg[0] | cap_run`
(1 ПТ в IO-MC) — во время захвата TX='1', джанк сдвига в линию не выходит.

Тайминг захвата: старт — на тик после первого `!WRn` (перепад state в T2),
10 тиков = ~440 нс от спада WR#. Окно валидности AH-пинов: CPU держит адрес
весь цикл записи и флоатит только после HLDA = ~650–700 нс от спада WR# —
запас ≥130 нс. Протокол **полностью тот же** (`[hi][lo][data]`, бит 520 нс)
— ПК-софт не меняется.

## Протокол (не изменился с v2)

| Параметр | Значение |
|---|---|
| Триггер | запись в ОЗУ 8000h–FFFFh: `!IOM && A15 && S0 && !S1` (статус ВМ85А: MW = IO/M#=0, S1=0, S0=1; стабилен с начала цикла) |
| Исключение | страница **FFh** (`EXCL_PAGE`): стек/переменные fw_mon FFE8–FFF8 — мимо потока и **без HOLD**; `8'h00` = без исключений |
| Пакет | **3 байта 8N1**: `[A15..A8][A7..A0][данные]`; A15 в hi-байте всегда 1 |
| Бод | **1 923 077,8** (`BAUD_DIV = 13`; бит ровно 520 нс) |
| Задержка | ~16–18 мкс на запись (HOLD = T1 → конец пакета, 30 бит) |
| Потолок | ~55 тыс. записей/с; экран 80×25 ≈ 36 мс |

## Как это работает (одна запись в ОЗУ)

```
T1 (ALE=1): win_hit = !IOM && A15 && S0 && !S1 && (ah != FFh) -> hold_req=1
            -> HOLD(P81) - ВМ85А сэмплирует его в T2 ЭТОГО ЖЕ цикла
T2 (1-й тик !WRn): данные записи -> bus_reg (штатный захват v3);
            cap_run=1: 10 тиков - кадр [0, A8..A15, 1] сдвигом собирается
            в shreg (AH-пины живы весь цикл записи); затем TX='0' - старт
конец кадра 1: загрузка lo (addr_latch); конец кадра 2: загрузка data
            (bus_reg); конец кадра 3 (стоп): shreg -> idle, hold_req=0 -
            CPU покидает HLDA ПОСЛЕ конца пакета (раньше нельзя: hi
            следующей записи попал бы в работающий сериализатор)
```

Пока CPU вне шины (`tx_hold = hold_req | hlda_q`), выбор памяти гасится
жёстко (`CS_n`/`CSr_n` = 1); выбор ОЗУ в WB — от состояния FSM (п.16 базы).
Защитная ветка: hold_req, не подкреплённый пакетом (глюк S0/S1), снимается
при HLDA + FSM=IDLE — пинг-понг 1–2 мкс.

## Правила для прошивки

1. Писать в ОЗУ можно **куда угодно** — логгер прозрачен (writeback v3
   доезжает до SRAM штатно).
2. Стек fw_mon (FFE8–FFF8) — в странице-исключении: CALL/PUSH не тормозят
   и в поток не пишутся.
3. Плотные записи троттлятся до ~55 тыс./с; для «текстового экрана»
   незаметно.

## Сторона ПК

Приёмник 1 923 077 8N1, кадры тройками `[hi][lo][data]`; фильтрация и
рендер — целиком на ПК.

```python
import serial
s = serial.Serial("/dev/ttyUSB0", 1923077)      # ядро >=2.6.32, драйвер ch341
# Если ОС/драйвер не берёт произвольную ставку - ioctl(TCSETS2) c BOTHER:
import fcntl, termios, struct
def set_custom_baud(fd, baud):
    TCSETS2 = 0x402C742F                        # x86_64/aarch64
    cflag = termios.CS8 | termios.CREAD | termios.CLOCAL | termios.BOTHER
    buf  = struct.pack("IIII", 0, 0, cflag, 0)  # iflag/oflag/cflag/lflag
    buf += struct.pack("B", 0) + bytes(19)      # c_line + c_cc[19]
    buf += struct.pack("II", baud, baud)        # ispeed/ospeed (всего 44 байта)
    fcntl.ioctl(fd, TCSETS2, buf)
# разбор: поток байт группами по 3: addr = hi<<8 | lo; data = третий байт.
# ПК сам решает: addr в регионе экрана -> рисовать, иначе -> лог.
```

Windows (CH341SER): pyserial принимает 1923077 напрямую (SetCommState);
проверить на стенде.

# v2-логгер: параллельный захват hi (СОХРАНЁН — план Б через Collapsing Input Limit)

**Статус:** фит 11-1 — Placement Failed (входы ФБ 216/216, см. разбор выше).
RTL `top_txclient_v2_utf8.v` / `top_txclient_v2.v`, модель
`scripts/sim_txclient_v2.py` (37/37), `scripts/tb_txclient_v2.v`. Идея была
честная: hi-байт грузится параллельно в shreg стробом захвата T2 — но
`ah_bus` лезет во все ФБ с триггерами shreg. Если v3 по какой-то причине не
ляжет — пробовать v2 с **Collapsing Input Limit 20–24** (запас МЦ позволяет
хелперы). Протокол и всё остальное — как у v3.

## Прочее (общее для v2/v3)

- Релиз HOLD — только в конце пакета: hi следующей записи при работающем
  CPU попал бы в работающий сериализатор и испортил хвост пакета №1;
  бэку-ту-бэк при этом беспотерь.
- Классификация по статусу S0/S1: чтения не тормозят вовсе (в v1 чтение
  окна = пинг-понг HOLD-HLDA); при полном ОЗУ это обязательно.

# v1-окно: монитор записей CPU в страницу F0xx (дешёвая альтернатива)

**Статус:** 2 байта, HOLD на голову пакета, ~77 тыс. записей/с, прогноз
~104/108 МЦ — если полный лог ОЗУ не нужен, а окно 256 байт устраивает.
RTL `top_txclient_v1_utf8.v` / `top_txclient_v1.v`, UCF
`top_txclient*.ucf`, верификация `scripts/sim_txclient.py` (29/29 ПАСС) +
`scripts/tb_txclient.v`.

## Протокол

| Параметр | Значение |
|---|---|
| Окно | страница **F000h–F0FFh** (`localparam WIN_PAGE = 8'hF0`) |
| Триггер | запись в память (`IOM=0`, `WR#=0`) с адресом страницы |
| Пакет | **2 байта 8N1**: `[адрес A0–A7][данные]`; старший байт адреса = F0h — константа |
| Бод | **1 923 077,8** (`BAUD_DIV = 13`) |
| Задержка вывода | ~11–13 мкс на запись (CPU заморожен только на голову пакета) |
| Потолок | ~77 тыс. записей/с |

## Как это работает (одна запись в окно)

```
T1 (ALE=1): декод win_hit = !IOM && {A15..A8}==F0h  ->  hold_req=1 -> HOLD(P81)
            (HOLD стабилен задолго до T2 -> ВМ85А сэмплирует его в T2 ЭТОГО ЖЕ
             цикла, HLDA - в конце его же; addr_latch/bus_reg не перезаписать)
T2:         данные записи -> bus_reg (штатный захват v3), WR# отработал
WB1..WB4:   writeback в ОЗУ КАК В v3.9.2 (запись не теряется и не дублируется)
HLDA:       CPU отпустил шину; FSM вернулась в IDLE ->
            пакет: [addr_latch][bus_reg], 20 бит, 10,4 мкс
2-й байт:   в момент его загрузки в shreg hold_req/tx_req СНИМАЮТСЯ - CPU
            работает, пока хвост пакета доезжает
```

Во время окна «CPU вне шины» (`tx_hold = hold_req | hlda_q`) выбор памяти
гасится жёстко (`CS_n`/`CSr_n` = 1): в HLDA процессор **флоатит** A15/IOM, и
живой декод выбирал бы ОЗУ/ПЗУ случайно. В WB выбор ОЗУ — по-прежнему от
FSM (п.16 базы). Заодно гейт закрывает окно «HOLD снят, HLDA ещё не упал».

HOLD берётся именно в **T1** цикла записи (а не по факту WR#): HOLD, поднятый
в T1, гарантированно сэмплируется ВМ85А в T2 этого же машинного цикла —
грант без промежуточных циклов, зафиксированный `addr_latch`/`bus_reg`
корректен всегда. Релиз — на загрузке 2-го байта.

## Почему в v1 было 2 байта (история вопроса о «4К»)

3-байтовый пакет (hi+lo+data) требует +8 триггеров под захват A8–A15: во
время HLDA наблюдатели AH8–AH14/A15 **флоат**, читать их на передаче нельзя.
От фита v3.9.2 это 85 − 3 (soft-UART) + 22 лог. МЦ txclient = ~104/108; плюс
8 МЦ под hi = 112 — **не лезет** в 108. **В v2/v3 вывод пересмотрен**: в v2
hi-байт грузится параллельно в shreg (без +8 FF, но фит не лёг по входам
ФБ), в v3 — сериально с живых пинов (и дёшево, и влезает).

## Правила для прошивки (v1)

1. Окно **только ЗАПИСЫВАТЬ**: чтение из F0xx тоже замирает CPU на один
   цикл (пинг-понг HOLD-HLDA) — без пакета, просто ~1–2 мкс простоя.
2. Код из окна **не исполнять** (выборка команды — тот же «цикл чтения»).
3. Никаких портов не нужно; стек/переменные монитора (FFE8–FFF8) окно
   не задевает.

## Сторона ПК (v1)

Приёмник 1 923 077 8N1, кадры парами `[lo][data]`, страница F0 — константа.

# v3.10-порт: терминальный вывод через захват записи в порт 07h (сохранено)

**Статус:** RTL готов, верифицирован цикл-точной моделью (33/33 PASS, `sim_txclient.py` в корне).
Фит в ISE НЕ выполнялся. База: **v3.9.2** — всё, кроме TX-тракта, бит-в-бит v3.9.2.

## Идея

Передатчик пишет **только то, что процессор пишет в область вывода**. CPLD ловит
запись в порт **07h** и пересылает байт в CH340G своим UART. Адрес на провод не
выносится — ПК знает, что весь поток = вывод терминала. SOD-транзит (CPU
бит-бэнжал SOD → CPLD → CH340, v3.7) удалён; приём (CH340 → CPLD → SID, RIM 20h)
не тронут. **Вопрос владельца «зачем порт 07h» закрыт**: это был триггер v3.10;
в оконной/логгерной схеме порты не нужны вовсе (04h–07h в v3.9.2 — резерв от
удалённого UART, Task 69).

## Протокол

| Операция | Смысл |
|---|---|
| `OUT 07h, A` | символ в терминал ПК (UART 115200 8N1, нога P39 → CH340G.RXD) |
| `IN 07h` | бит 0 = **TXRDY** (1 = окно приёма открыто, запись будет принята); биты 7–1 = 0 |
| `OUT 00h/01h/02h`, `IN 03h` | без изменений (сегменты / разряды+SND / колонки / KBROW) |
| `OUT 04h…06h` | резерв, как в v3.9.2 |

- Декод порта — по **A2–A0** (стиль проекта): алиасы `0Fh, 17h, …` тоже работают.
- Кадр: старт + 8 бит (LSB first) + стоп; **бит = 217 тиков 25 МГц = 8,68 мкс =
  115207,4 бода (+0,006 % к 115200; CH340G на 115200 точен)**.
- `RCONST` — параметр модуля `serial_tx` (216 по умолчанию).

## Контракт прошивки

```asm
; putchar: символ в C — без потерь, темп до ~12,5 тыс. знаков/с
PUTC:   IN    A,(07h)     ; 10T
        RRC               ;  4T   ; бит 0 -> CY
        JC    PUTC_OK     ; 10T/7T
        JP    PUTC        ; ожидание (период опроса 21T = 5,9 мкс)
PUTC_OK:MOV   A,C
        OUT   (07h),A
```

- **Пишешь без опроса — байты теряются** (окно закрыто → строб игнорируется).
  Это документированное поведение, а не дефект.
- TXRDY=1 гарантирует приём: писатель один (CPU), окно непрерывно до загрузки.

## Безопасность по построению (+2 МЦ к голой схеме uart.v)

Маркер `busy` в uart.v падает **на старте бита b7** — перезагрузка, попав в первые
50 % бита b7, портила бы ещё не отобранный приёмником бит (запас съедает
квантование CH340 ±0,2 %). В v3.10 окно приёма

```
tx_acc = !busy & !stop_q & !busy_d          (TXRDY = tx_acc)
stop_q: set — падение busy (начался b7); clear — bittick через бит (начался стоп)
```

открывается **только со старт-бита стопа** — перезагрузка физически не может
попасть в биты данных (худший случай — срезанный стоп = FE-флаг у ПК, байты
целы). Плюс 1-тактный строб `tx_send_q` вместо защёлкивания уровнем.

## Вердикт «холд vs буфер» (вопрос владельца)

Буфер: WR# к моменту захвата уже отработан, HOLD лишь придерживал бы следующий
доступ; холд = те же 21 МЦ + FSM HOLD/HLDA (+5..8) = 106..109/108 на грани
непомещения, с троттлингом CPU и касанием ноги 81 (PGND). Буфер с TXRDY-поллингом
даёт те же гарантии без потерь (период опроса 21T = 5,9 мкс < бит 8,68 мкс).
**В v1–v3 вердикт пересмотрен**: там HOLD несёт другую функцию — не защита
захвата (адрес/данные и так защёлкнуты FSM), а удержание шины, пока пакет не
загружен; в v2/v3 — ещё и гарантия валидности трёх источников пакета
(hi/lo/data) до конца передачи.
