# beta/txclient — вывод CPU → ПК без классического UART-терминала

База версий v1–v6: **v3.9.2** (`beta/lowsize/top_suart_por6_v392_utf8.v`,
фит 10-30 8:32PM: 85/108 МЦ, 209/540 ПТ, 180/216 вх. ФБ, 54 триггера —
принята владельцем). **База v7: v3.9.3** (сброс логики → сеть GSR, фит 11-2
«GSR : 1 1», железо ПАСС; задание владельца 11-3 «на основе последнего
lowsize дизайна можно попробовать txclient»; исходная директива: *«нам не нужен TX [терминальный] — убери
SOD; будем знать, когда процессор пишет в область вывода UART; дизайн в
beta/txclient»*; развитие: *«на ПК определяется запись в какой регион
происходит и на ПК же принимается решение транслировать данные … в
примитивный текстовый экран»*; *«захват большей страницы ОЗУ чем 4К не
получается?»* — **получается: txclient захватывает окно ОЗУ с полным 16-битным
адресом**. Фиты v2 (11-1 9:26AM), v3 (11-1 11:02AM), v4 (11-1 6:16PM) и v5
(11-1 7:31PM) у владельца — все четыре **Placement Failed** (входы ФБ

6:46PM) — тоже **Placement Failed**, но впервые стена — ёмкость/упаковка
(потребность 114 МЦ против 108, вх. ФБ 208/216; GSR-мера п.24 при этом
СРАБОТАЛА: литералы сброса 306 → 5, ПТ 383 → 310) — разбор в разделе v7;
на вопрос владельца
*«может всё таки перейти к захвату конкретного региона ОЗУ, скажем
8000-C000?»* — ответ **ДА** (окно 8000h–BFFFh принято в v5); **v6 = сдвиг

**11-2**: v6 у владельца не прошёл даже HDL-компилятор — XST
`ERROR:HDLCompilers:28 "'…' has not been declared"`, ×17 (`al_shift`,
`br_shift`, `bit_cnt`, `tx_byte`). Разбор: в коммиченном v6 все объявления

`rtl_txclient/top_txclient_v6.v` без блока объявлений. Страховка от всего
класса: в v6 (правка п.23.1, поведение не менялось) объявления сериализатора
подняты выше ВСЕХ использований (блок — перед шинным движком; внутри блока
регистры выше `in_cap`/`in_frame`) + новый `scripts/check_decl_order.py` —
статическая проверка «объявление раньше использования» до запуска ISE (на

строже XST, чтобы исходник проходил и iverilog, которым владелец гоняет tb).
Владельцу: пересинхронизировать файл в `rtl_txclient/` и перекомпилировать.

## Лекарство v6: сдвиг источников кадров 2/3 к LSB (инжекция одного провода)

`in_frame` в v5 выбирал бит (bc−2) из ПОЛНОГО регистра (8+8 источников +
выбор) — фиттер сворачивал его в `shreg<8>.D` (26 вх.). Лечение:

- **addr_latch и bus_reg СДВИГАЮТСЯ ВПРАВО (к LSB) синхронно с
  инжекцией**: тик adv_q с bc=2..9 кадра N читает `addr_latch[0]`/
  `bus_reg[0]` И сдвигает регистр (`{1'b0, r[7:1]}`); за 8 тиков мимо
  инжекции проходят ВСЕ 8 бит (A0..A7 / D0..D7), к концу кадра регистр
  = 0. `in_frame` худеет с 26 до ~8 входов (bc, tx_byte, al[0], br[0],
  константы); mux-хелперы с литералами D(i)/addr_latch(i), i>0 — УМИРАЮТ;
  D-функция shreg<8> становится размещаемой. **НОВЫХ ТРИГГЕРОВ НОЛЬ** —
  регистры уже есть; цена — 3 ПТ на бит (терм сдвига) в addr_latch/bus_reg.
- **Безопасность базы**: сдвиг стартует с bc=2 ПЕРВОГО кадра — ~1,9 мкс
  после WR#(вверх); writeback (WB1..4, A/D-пины гонят эти регистры)
  кончается через ~0,2 мкс — ЗАПАС ~1,7 мкс. Вне пакета сдвига НЕТ
  (условия TXB_HI/TXB_LO + adv_q); загрузка T1/T2 — прежняя (приоритет
  выше — else-if в шинном движке).
- Прогноз: **~102–106/108 МЦ** (−4..−6 хелпер-МЦ, дубли A<3:4>_BUFR
  складываются обратно в FB1), **вх. ФБ ~185–205/216**, ПТ ~350–380.
  Провод НЕ изменился ([hi][lo][data] 8N1, бит 520 нс) — ПК-софт БЕЗ ПРАВОК.
- План Б: (а) ISE Fit → Properties → **Collapsing Input Limit 36 → 24–28**;
  (б) окно ЕЩЁ уже (A15 & !AH14 & !AH13 = 8000–9FFFh); (в) BAUD_DIV 13 → 16
  (бод 1 562 500, натуральный wrap минус декод ==12); (г) por_sh 8 → 4
  (БАЗА — только с одобрения!).

## Лекарство v5 (история): окно 8000-BFFF + сериальная предзагрузка кадров 2/3

Хелперы adv_q/ld_q своё сделали (декоды кадров больше не копируются в
биты shreg — провал v3 снят), но в фите v4 осталось три жира:

1. **Параллельные загрузки** `{addr_latch / bus_reg, 1'b0}` в конце
   кадров тащат в каждый ФБ с битом shreg 8+8 источников данных + декоды
   ld_q/tx_byte.
2. **9-литеральный строб захвата** (`state==S_T2 && !WRn && !wr_seen &&
   hold_req && TXB_IDLE`) с предзагрузкой `shreg<=000` размазан по 13
   регистрам (9 бит shreg + 4 baud_cnt).
3. **win_hit с 7-литеральным декодом EXCL_PAGE** держит AH8–14 в FB6:
   `hold_req__or0000_D2` = 10 ПТ/23 вх., HOLD = 8 ПТ/19 вх.

Лекарства:

- **Окно = 8000h–BFFFh** (решение владельца, `A15 && !AH14` — 2 литерала
  вместо 7): AH8–13 уходят из FB6, `hold_req__or0000_D2` растворяется
  (hold_req.D ~3 ПТ/~11 вх., HOLD ~2–3 ПТ/~9 вх.); стек fw_mon (FFEx–FFF8)
  и C000–FFFF — вне окна ПО ПОСТРОЕНИЮ.
- **Кадры 2/3 грузятся в shreg СЕРИАЛЬНО, во время передачи предыдущего**
  (классический двойной буфер): вход shreg<8> на тике bc кадра N = бит
  (bc−1) кадра N+1: bc0 → '1' (стоп текущего), bc1 → '0' (старт
  следующего — только если кадр ЕСТЬ), bc2..9 → addr_latch[bc−2] (кадр 2)
  / bus_reg[bc−2] (кадр 3) / '1' (кадра 4 нет — idle). Параллельных
  загрузок больше НЕТ: D-функция бита shreg<8:1> = 3 ПТ/~5 входов — все
  9 бит ложатся в ОДИН ФБ по построению; источники данных — только в
  мультиплексорах in_cap/in_frame (каждый в своём МЦ).
- **Строб захвата = только взвод cap_run** (8 литералов в ОДНОМ триггере
  вместо размазки на 13): предзагрузка shreg<=000 УДАЛЕНА (старт-бит
  заходит через in_cap на bc==0), счётчики в стробе не трогаются
  (bit_cnt==0 в TXB_IDLE — структурный инвариант: ld_q конца кадра 3 и
  сброс пишут 0), !wr_seen удалена (повторный старт блокирует !cap_run
  со 2-го тика !WRn — состояние то же).

Захват hi: 8 → 9 тиков (bc 0..8) — последнее чтение AH на 400-й нс от
спада WR# (окно валидности AH 650–700 нс — запас ~250 нс; в v4 было 360).
Старт-бит кадра 1 виден на тике 10 от первого !WRn (в v4 — на 9-м);
сетка дальше ТА ЖЕ: baud_cnt<=1 в конце захвата, старт-бит ровно 13
тиков, зазоры 0, кадр ровно 130 тиков. **Провод НЕ изменился**:
[hi][lo][data] 8N1, бит 520 нс — ПК-софт БЕЗ ПРАВОК.

## Лекарство v4 (история): регистровые хелперы adv_q/ld_q + shreg 9 бит

Два триггера:

```
adv = (tx_byte != IDLE) && baud_tick;   ld = adv && (bit_cnt == 9);
adv_q <= adv;   ld_q <= ld;
```

**Выход триггера фиттер НЕ МОЖЕТ коллапсировать в D-функции потребителей**
— каждый ФБ с битом shreg платит 1 вход вместо ~10 развёрнутых декодов.
D-функция бита shreg сжимается с 16–22 до ~9 входов (adv_q, ld_q, сосед,
источник, tx-селект, RST/por) → все 9 бит shreg упаковываются в 1–2 ФБ
(~45–50 слотов вместо ~80–100); hold_req.D ~24 → ~20.

Плюс shreg 10 → 9 бит: **стоп-бит подставляет ИНЖЕКТ '1'** при сдвиге
(`{1'b1, shreg[8:1]}`); после 9 сдвигов shreg сам приходит в все-'1' =
idle — отдельная idle-загрузка (10'h3FF в v2/v3) УДАЛЕНА. Захват hi
10 → 8 тиков: старт-бит **предзагружается** (`shreg <= 9'h000` на старте
захвата: b0=0 = старт, b8..b1 = 0 вымываются 8 сдвигами), мультиплексор
входа стал **чистым 8:1** (`ah_rev[bit_cnt[2:0]]` — без констант старта/
стопа и без 3-бит вычитания v3).

Фазировка сетки: в конце захвата `baud_cnt <= 4'd1` (НЕ 0) — первый сдвиг
кадра ровно на 13-м такте после спада TX (старт-бит ровно 13 тиков);
загрузки кадров — по ld_q (на такт позже baud_tick), baud_cnt НЕ трогается
→ сетка 13 тиков и зазоры 0 точные (симуляция: фронты на сетке S1+130·k).

**Провод НЕ изменился вовсе**: `[hi][lo][data]` 8N1, бит 520 нс, кадр
ровно 130 тиков, зазоры 0, HOLD до конца пакета, релиз в стоп-бите кадра 3
(+1 такт к v3 — не видно). ПК-софт БЕЗ ПРАВОК.

Механика: `cap_run` ставится тем же стробом (`state==S_T2 && !WRn &&
!wr_seen && hold_req && TXB_IDLE`); счётчик фазы — штатный `bit_cnt`
(0..7 в захвате); во время фазы `case(tx_byte)` не выполняется (защитный
релиз IDLE недостижим); `TX = shreg[0] | cap_run` (1 ПТ в IO-MC) — во
время захвата TX='1', джанк сдвига и предзагрузка в линию не выходят.

Тайминг захвата: старт — на тик после первого `!WRn` (перепад state в T2),
8 тиков = ~320 нс от спада WR#. Окно валидности AH-пинов: ~650–700 нс от
спада WR# — запас вырос (был ≥130 нс при 10 тиках).

## Протокол (не изменился с v2; окно — новое в v5)

| Параметр | Значение |
|---|---|
| Триггер | запись в ОЗУ **окна 8000h–BFFFh**: `!IOM && A15 && !AH14 && S0 && !S1` (статус ВМ85А: MW = IO/M#=0, S1=0, S0=1; стабилен с начала цикла; решение владельца, п.22) |
| Вне окна | **по построению**: стек/переменные fw_mon FFE8–FFF8 и вся область C000–FFFF — мимо потока и **без HOLD** (декод-исключение EXCL_PAGE удалён — экономия 6 литералов) |
| Пакет | **3 байта 8N1**: `[A15..A8][A7..A0][данные]`; A15 в hi-байте всегда 1 (в окне — A15=1 и A14=0) |
| Бод | **1 923 077,8** (`BAUD_DIV = 13`; бит ровно 520 нс) |
| Задержка | ~16–18 мкс на запись (HOLD = T1 → конец пакета, 30 бит) |
| Потолок | ~55 тыс. записей/с; экран 80×25 ≈ 36 мс |

## Как это работает (одна запись в ОЗУ)

```
T1 (ALE=1): win_hit = !IOM && A15 && !AH14 && S0 && !S1 (окно 8000-BFFF, п.22)
            -> hold_req=1 -> HOLD(P81) - ВМ85А сэмплирует его в T2 ЭТОГО ЖЕ цикла
T2 (1-й тик !WRn): данные записи -> bus_reg (штатный захват v3);
            cap_run=1 (ТОЛЬКО взвод, п.22): 9 тиков - старт-бит ('0' на bc==0)
            и A8..A15 сдвигом с AH-пинов (AH живы весь цикл записи);
            затем TX='0' - старт (виден на тике 10 от первого !WRn)
кадры 1/2: следующий байт (addr_latch/bus_reg) СЕРИАЛЬНО предзагружается
            во время передачи текущего: инжекция ОДНОГО провода ([0]),
            источник СДВИГАЕТСЯ к LSB (п.23); на ld_q меняются только
            tx_byte/hold_req
конец кадра 3 (стоп): tx_byte->IDLE, hold_req=0 (shreg уже все '1' -
            in_frame кадра 3 льёт '1') - CPU покидает HLDA ПОСЛЕ конца
            пакета (раньше нельзя: hi следующей записи попал бы в
            работающий сериализатор)
```

Пока CPU вне шины (`tx_hold = hold_req | hlda_q`), выбор памяти гасится
жёстко (`CS_n`/`CSr_n` = 1); выбор ОЗУ в WB — от состояния FSM (п.16 базы).
Защитная ветка: hold_req, не подкреплённый пакетом (глюк S0/S1), снимается
при HLDA + FSM=IDLE — пинг-понг 1–2 мкс.

## Правила для прошивки

1. Писать в ОЗУ можно **куда угодно** — логгер прозрачен (writeback v3
   доезжает до SRAM штатно).
2. Стек fw_mon (FFE8–FFF8) и вся область **C000–FFFF — вне окна** (п.22):
   CALL/PUSH не тормозят и в поток не пишутся.
3. Плотные записи троттлятся до ~55 тыс./с; для «текстового экрана»
   незаметно.
4. **Видеобуфер должен лежать в 8000h–BFFFh** — записи выше BFFF на ПК
   не попадают (если понадобится шире — вернуть декод EXCL_PAGE:
   +6 литералов, не лезло в v2–v4).

## Сторона ПК

Приёмник 1 923 077 8N1, кадры тройками `[hi][lo][data]`; фильтрация и
рендер — целиком на ПК.

```python
import serial
s = serial.Serial("/dev/ttyUSB0", 1923077)      # ядро >=2.6.32, драйвер ch341
# Если ОС/драйвер не берёт произвольную ставку - ioctl(TCSETS2) c BOTHER:
import fcntl, termios, struct
def set_custom_baud(fd, baud):
    TCSETS2 = 0x402C742F                        # x86_64/aarch64
    cflag = termios.CS8 | termios.CREAD | termios.CLOCAL | termios.BOTHER
    buf  = struct.pack("IIII", 0, 0, cflag, 0)  # iflag/oflag/cflag/lflag
    buf += struct.pack("B", 0) + bytes(19)      # c_line + c_cc[19]
    buf += struct.pack("II", baud, baud)        # ispeed/ospeed (всего 44 байта)
    fcntl.ioctl(fd, TCSETS2, buf)
# разбор: поток байт группами по 3: addr = hi<<8 | lo; data = третий байт.
# ПК сам решает: addr в регионе экрана -> рисовать, иначе -> лог.
```

Windows (CH341SER): pyserial принимает 1923077 напрямую (SetCommState);
проверить на стенде.

# v1-окно: монитор записей CPU в страницу F0xx (дешёвая альтернатива)

**Статус:** 2 байта, HOLD на голову пакета, ~77 тыс. записей/с, прогноз
~104/108 МЦ — если полный лог ОЗУ не нужен, а окно 256 байт устраивает.
RTL `top_txclient_v1_utf8.v` / `top_txclient_v1.v`, UCF
`top_txclient*.ucf`, верификация `scripts/sim_txclient.py` (29/29 ПАСС) +
`scripts/tb_txclient.v`.

## Протокол

| Параметр | Значение |
|---|---|
| Окно | страница **F000h–F0FFh** (`localparam WIN_PAGE = 8'hF0`) |
| Триггер | запись в память (`IOM=0`, `WR#=0`) с адресом страницы |
| Пакет | **2 байта 8N1**: `[адрес A0–A7][данные]`; старший байт адреса = F0h — константа |
| Бод | **1 923 077,8** (`BAUD_DIV = 13`) |
| Задержка вывода | ~11–13 мкс на запись (CPU заморожен только на голову пакета) |
| Потолок | ~77 тыс. записей/с |

## Как это работает (одна запись в окно)

```
T1 (ALE=1): декод win_hit = !IOM && {A15..A8}==F0h  ->  hold_req=1 -> HOLD(P81)
            (HOLD стабилен задолго до T2 -> ВМ85А сэмплирует его в T2 ЭТОГО ЖЕ
             цикла, HLDA - в конце его же; addr_latch/bus_reg не перезаписать)
T2:         данные записи -> bus_reg (штатный захват v3), WR# отработал
WB1..WB4:   writeback в ОЗУ КАК В v3.9.2 (запись не теряется и не дублируется)
HLDA:       CPU отпустил шину; FSM вернулась в IDLE ->
            пакет: [addr_latch][bus_reg], 20 бит, 10,4 мкс
2-й байт:   в момент его загрузки в shreg hold_req/tx_req СНИМАЮТСЯ - CPU
            работает, пока хвост пакета доезжает
```

Во время окна «CPU вне шины» (`tx_hold = hold_req | hlda_q`) выбор памяти
гасится жёстко (`CS_n`/`CSr_n` = 1): в HLDA процессор **флоатит** A15/IOM, и
живой декод выбирал бы ОЗУ/ПЗУ случайно. В WB выбор ОЗУ — по-прежнему от
FSM (п.16 базы). Заодно гейт закрывает окно «HOLD снят, HLDA ещё не упал».

HOLD берётся именно в **T1** цикла записи (а не по факту WR#): HOLD, поднятый
в T1, гарантированно сэмплируется ВМ85А в T2 этого же машинного цикла —
грант без промежуточных циклов, зафиксированный `addr_latch`/`bus_reg`
корректен всегда. Релиз — на загрузке 2-го байта.

## Почему в v1 было 2 байта (история вопроса о «4К»)

3-байтовый пакет (hi+lo+data) требует +8 триггеров под захват A8–A15: во
время HLDA наблюдатели AH8–AH14/A15 **флоат**, читать их на передаче нельзя.
От фита v3.9.2 это 85 − 3 (soft-UART) + 22 лог. МЦ txclient = ~104/108; плюс
8 МЦ под hi = 112 — **не лезет** в 108. **В v2/v3 вывод пересмотрен**: в v2
hi-байт грузится параллельно в shreg (без +8 FF, но фит не лёг по входам
ФБ), в v3 — сериально с живых пинов (и дёшево, и влезает).

## Правила для прошивки (v1)

1. Окно **только ЗАПИСЫВАТЬ**: чтение из F0xx тоже замирает CPU на один
   цикл (пинг-понг HOLD-HLDA) — без пакета, просто ~1–2 мкс простоя.
2. Код из окна **не исполнять** (выборка команды — тот же «цикл чтения»).
3. Никаких портов не нужно; стек/переменные монитора (FFE8–FFF8) окно
   не задевает.

## Сторона ПК (v1)

Приёмник 1 923 077 8N1, кадры парами `[lo][data]`, страница F0 — константа.

# v3.10-порт: терминальный вывод через захват записи в порт 07h (сохранено)

**Статус:** RTL готов, верифицирован цикл-точной моделью (33/33 PASS, `sim_txclient.py` в корне).
Фит в ISE НЕ выполнялся. База: **v3.9.2** — всё, кроме TX-тракта, бит-в-бит v3.9.2.

## Идея

Передатчик пишет **только то, что процессор пишет в область вывода**. CPLD ловит
запись в порт **07h** и пересылает байт в CH340G своим UART. Адрес на провод не
выносится — ПК знает, что весь поток = вывод терминала. SOD-транзит (CPU
бит-бэнжал SOD → CPLD → CH340, v3.7) удалён; приём (CH340 → CPLD → SID, RIM 20h)
не тронут. **Вопрос владельца «зачем порт 07h» закрыт**: это был триггер v3.10;
в оконной/логгерной схеме порты не нужны вовсе (04h–07h в v3.9.2 — резерв от
удалённого UART, Task 69).

## Протокол

| Операция | Смысл |
|---|---|
| `OUT 07h, A` | символ в терминал ПК (UART 115200 8N1, нога P39 → CH340G.RXD) |
| `IN 07h` | бит 0 = **TXRDY** (1 = окно приёма открыто, запись будет принята); биты 7–1 = 0 |
| `OUT 00h/01h/02h`, `IN 03h` | без изменений (сегменты / разряды+SND / колонки / KBROW) |
| `OUT 04h…06h` | резерв, как в v3.9.2 |

- Декод порта — по **A2–A0** (стиль проекта): алиасы `0Fh, 17h, …` тоже работают.
- Кадр: старт + 8 бит (LSB first) + стоп; **бит = 217 тиков 25 МГц = 8,68 мкс =
  115207,4 бода (+0,006 % к 115200; CH340G на 115200 точен)**.
- `RCONST` — параметр модуля `serial_tx` (216 по умолчанию).

## Контракт прошивки

```asm
; putchar: символ в C — без потерь, темп до ~12,5 тыс. знаков/с
PUTC:   IN    A,(07h)     ; 10T
        RRC               ;  4T   ; бит 0 -> CY
        JC    PUTC_OK     ; 10T/7T
        JP    PUTC        ; ожидание (период опроса 21T = 5,9 мкс)
PUTC_OK:MOV   A,C
        OUT   (07h),A
```

- **Пишешь без опроса — байты теряются** (окно закрыто → строб игнорируется).
  Это документированное поведение, а не дефект.
- TXRDY=1 гарантирует приём: писатель один (CPU), окно непрерывно до загрузки.

## Безопасность по построению (+2 МЦ к голой схеме uart.v)

Маркер `busy` в uart.v падает **на старте бита b7** — перезагрузка, попав в первые
50 % бита b7, портила бы ещё не отобранный приёмником бит (запас съедает
квантование CH340 ±0,2 %). В v3.10 окно приёма

```
tx_acc = !busy & !stop_q & !busy_d          (TXRDY = tx_acc)
stop_q: set — падение busy (начался b7); clear — bittick через бит (начался стоп)
```

открывается **только со старт-бита стопа** — перезагрузка физически не может
попасть в биты данных (худший случай — срезанный стоп = FE-флаг у ПК, байты
целы). Плюс 1-тактный строб `tx_send_q` вместо защёлкивания уровнем.

## Вердикт «холд vs буфер» (вопрос владельца)

Буфер: WR# к моменту захвата уже отработан, HOLD лишь придерживал бы следующий
доступ; холд = те же 21 МЦ + FSM HOLD/HLDA (+5..8) = 106..109/108 на грани
непомещения, с троттлингом CPU и касанием ноги 81 (PGND). Буфер с TXRDY-поллингом
даёт те же гарантии без потерь (период опроса 21T = 5,9 мкс < бит 8,68 мкс).
**В v1–v3 вердикт пересмотрен**: там HOLD несёт другую функцию — не защита
захвата (адрес/данные и так защёлкнуты FSM), а удержание шины, пока пакет не
загружен; в v2–v4 — ещё и гарантия валидности трёх источников пакета
(hi/lo/data) до конца передачи.
