# beta/txclient — вывод CPU → ПК без классического UART-терминала

База всех версий: **v3.9.2** (`beta/lowsize/top_suart_por6_v392_utf8.v`, фит
10-30 8:32PM: 85/108 МЦ, 209/540 ПТ, 180/216 вх. ФБ, 54 триггера — принята

# v2-логгер: монитор ЗАПИСЕЙ CPU В ОЗУ, полный 16-битный адрес (текущий кандидат)

## Ответ на вопрос владельца: почему «4К не получается» оказалось неверным

В v1 пакет был 2-байтовым `[адрес A0–A7][данные]`, а страница (F0h) —
константой: окно 256 байт. 3-байтовый пакет «в лоб» требует **+8 триггеров**
под захват A8–A15 — во время HLDA процессор **флоатит** AH-пины, читать их
на передаче нельзя; 85 − 3 + 22 + 8 = 112 > 108 МЦ — «не лезет» (промежуточный
вариант «4К» — захват A8–A11 в 4 FF — 108/108 впритык). **Трюк v2 снимает
+8 FF полностью**: hi-байт **не хранится в отдельном регистре** — он грузится
**прямо в shreg** стробом захвата T2 (первый тик `!WRn`: AH-пины ещё живы —
CPU в цикле записи, HOLD взят в T1) и уходит в линию **первым**. Байт 2 —
`addr_latch` (A0–A7), байт 3 — `bus_reg` (данные): оба уже в регистрах базы.
Регистров в txclient не прибавилось — **предел «больше 4К не получается»
снят: не 4К и не 8К — вся память 8000h–FFFFh с полным адресом в пакете**.

Цена трюка: HOLD держится **до конца пакета**. Релиз раньше конца невозможен:
байт 3 ещё не в shreg, а hi **следующей** записи при работающем CPU грузился
бы в работающий shreg — порча хвоста пакета №1.

Второе изменение v2 — **классификация цикла по статусу S0/S1** (ВМ85А: MW =
`IO/M#=0, S1=0, S0=1`; OF/MR = `S1=1`; HALT = `S0=S1=0`), а не «по факту WR#»:
HOLD взводится в T1 **только** для записей в ОЗУ. Чтения и исполнение кода не
тормозят **вовсе** (в v1 любое чтение окна = пинг-понг HOLD-HLDA 1–2 мкс; при
полном ОЗУ без S0/S1 замирал бы каждый доступ к памяти — S0/S1 в v2
обязательны, а не украшение).

## Протокол

| Параметр | Значение |
|---|---|
| Триггер | запись в ОЗУ 8000h–FFFFh: `!IOM && A15 && S0 && !S1` (статус стабилен с начала цикла, сэмплируется с ALE в T1) |
| Исключение | страница **FFh** (`EXCL_PAGE = 8'hFF`): стек/переменные fw_mon FFE8–FFF8 — мимо потока и **без HOLD** (иначе каждый CALL/PUSH +15,6…31 мкс); `8'h00` = без исключений |
| Пакет | **3 байта 8N1**: `[A15..A8][A7..A0][данные]`; A15 в hi-байте всегда 1 — ПК может сверять |
| Бод | **1 923 077,8** (`BAUD_DIV = 13`: 25 МГц/13; бит ровно 520 нс) |
| Задержка вывода | ~16–18 мкс на запись (HOLD = T1 → конец пакета, 30 бит × 520 нс) |
| Потолок | ~55 тыс. записей/с (v1: ~77 тыс.); экран 80×25 = 2000 байт ≈ 36 мс |

## Как это работает (одна запись в ОЗУ)

```
T1 (ALE=1): win_hit = !IOM && A15 && S0 && !S1 && (ah != FFh) -> hold_req=1
            -> HOLD(P81) - ВМ85А сэмплирует его в T2 ЭТОГО ЖЕ цикла
T2 (1-й тик !WRn): данные записи -> bus_reg (штатный захват v3);
            hi-байт адреса -> ПРЯМО В shreg (AH-пины живы!) и старт
            сериализации - байт 1 едет, пока идут WB1..WB4 и рукопожатие
            (TX - отдельная нога, с шиной не воюет; старт ДО HLDA)
конец байта 1: загрузка lo (addr_latch); конец байта 2: загрузка data
            (bus_reg); конец байта 3 (стоп-бит): shreg -> idle,
            hold_req=0 - CPU покидает HLDA ПОСЛЕ конца пакета
```

Пока CPU вне шины (`tx_hold = hold_req | hlda_q`), выбор памяти гасится
жёстко (`CS_n`/`CSr_n` = 1): в HLDA процессор **флоатит** A15/IOM — живой
декод выбирал бы ОЗУ/ПЗУ случайно (гейт закрывает и окно «HOLD снят, HLDA
ещё не упал»). Выбор ОЗУ в WB — по-прежнему от состояния FSM (п.16 базы).
Защитная ветка: если hold_req взвёлся, а пакет не стартовал (глюк
классификации S0/S1), при HLDA + FSM=IDLE hold_req снимается без пакета —
пинг-понг 1–2 мкс, как чтение в v1.

## Почему релиз — только в конце пакета

Три источника пакета «живут» по-разному: hi — только пока CPU в цикле записи
(потом шина уходит под HOLD или уезжает), lo — до следующего ALE, data — до
следующего захвата. Пока CPU заморожен (HOLD весь пакет), все три валидны;
стоят отпустить HOLD раньше конца пакета — hi следующей записи попадает в
работающий shreg и портит хвост текущего пакета. Бэку-ту-бэк при этом
беспотерь: пакет №2 стартует после полного освобождения shreg, следующая
запись CPU проходит сразу после релиза.

## Правила для прошивки

1. Писать в ОЗУ можно **куда угодно** — логгер прозрачен (запись доезжает до
   SRAM штатным writeback v3, потом уезжает в ПК).
2. Стек fw_mon (FFE8–FFF8) — в странице-исключении: CALL/PUSH не тормозят и
   в поток не пишутся. Другая страница-исключение — правка `EXCL_PAGE`.
3. Плотные записи в ОЗУ троттлятся до ~55 тыс./с (каждая ~16–18 мкс):
   memset 32К ≈ 0,6 с; для «текстового экрана» это незаметно.

## Сторона ПК

Приёмник 1 923 077 8N1, кадры тройками `[hi][lo][data]`; фильтрация по
региону и рендер (видеобуфер → примитивный текстовый экран) — целиком на ПК.

```python
import serial
s = serial.Serial("/dev/ttyUSB0", 1923077)      # ядро >=2.6.32, драйвер ch341
# Если ОС/драйвер не берёт произвольную ставку - ioctl(TCSETS2) c BOTHER:
import fcntl, termios, struct
def set_custom_baud(fd, baud):
    TCSETS2 = 0x402C742F                        # x86_64/aarch64
    cflag = termios.CS8 | termios.CREAD | termios.CLOCAL | termios.BOTHER
    buf  = struct.pack("IIII", 0, 0, cflag, 0)  # iflag/oflag/cflag/lflag
    buf += struct.pack("B", 0) + bytes(19)      # c_line + c_cc[19]
    buf += struct.pack("II", baud, baud)        # ispeed/ospeed (всего 44 байта)
    fcntl.ioctl(fd, TCSETS2, buf)
# разбор: поток байт группами по 3: addr = hi<<8 | lo; data = третий байт.
# ПК сам решает: addr в регионе экрана -> рисовать, иначе -> лог.
```

Windows (CH341SER): произвольная ставка задаётся через стандартный API
(SetCommState) — pyserial принимает 1923077 напрямую; проверить на стенде.

## Ресурсы / верификация v2

- Прогноз от фита v3.9.2 (85/108): **~103/108 МЦ** (85 − 3 soft-UART +
  21 лог. МЦ: hold_req, hlda_q, tx_byte<1:0>, bit_cnt<3:0>, baud_cnt<3:0>,
  shreg<9:1> + shreg[0] в IO-MC P39; хелперы декодов — до 104–105); tx_req
  удалён (−1 МЦ против v1); **+8 FF под A8–A15 НЕ нужны** — в этом весь трюк.
  ПТ ~240–260/540 (+8–16 на загрузку ah_bus в shreg, −8–10 на упрощение
  win_hit/релиза); вх. ФБ ~195/216 (+8: ah_bus в ФБ сериализатора; сами
  AH-пины уже в матрице с v1); ноги 72/81 — **UCF v1 без правок**
  (`top_txclient.ucf`: HOLD P81 = выход, S0 P94/S1 P89/AH8–AH14/A15 — входы).
- `scripts/sim_txclient_v2.py` — **37/37 ПАСС**: запись ОЗУ (3 кадра,
  содержимое hi/lo/data, сетка 13 тиков, зазоры 0, HOLD на весь пакет и
  релиз в стоп-бите кадра 3), гейты CS в tx_hold (/WE ровно 2 тика в WB),
  страница-исключение FFxx (без HOLD, шина прозрачна), запись в ПЗУ
  (отброс), IO-запись, **чтение ОЗУ без HOLD вовсе**, бэку-ту-бэк (6 кадров,
  без потерь, пауза между пакетами), ложная классификация (защитный релиз),
  сброс посреди пакета.
- `scripts/tb_txclient.v` → для владельца: `iverilog -o tb_v2.vvp
  scripts/tb_txclient_v2.v top_txclient_v2_utf8.v && vvp tb_v2.vvp`
  (в песочнице iverilog нет — эталон sim_txclient_v2.py).

## Что делать (v2)

1. Фит в ISE (этот .v + этот .ucf) → `.rpt` **на аудит до прошивки**:
   чек-лист — в шапке RTL (прогноз ~103/108 МЦ; `tx_req`/`sod_q`/`tx_pass`
   в нетлисте быть не должно; `shreg<0>` — в IO-MC P39; HOLD P81 = OUT;
   PGND = ровно 8 пинов без P81).
2. Прогнать `scripts/tb_txclient_v2.v` у владельца (эталон —
   `scripts/sim_txclient_v2.py`).
3. `.jed` в плату; осциллограф: TX idle '1', после записи в ОЗУ (не FFxx) —
   пакет 3 байта, бит 520 нс; HOLD '1' от T1 записи **до конца пакета**;
   HLDA между; чтения ОЗУ HOLD не дают.
4. ПК-приёмник (сниппет выше) — фильтрация региона и «текстовый экран»
   рисуются на стороне ПК.

# v1-окно: монитор записей CPU в страницу F0xx (предыдущий кандидат)

**Статус:** сохранён как дешёвая альтернатива (2 байта, HOLD на голову
пакета, ~77 тыс. записей/с) — если полный лог ОЗУ окажется не нужен, а
окно 256 байт устраивает. RTL `top_txclient_v1_utf8.v` / `top_txclient_v1.v`,
UCF `top_txclient*.ucf`, верификация `scripts/sim_txclient.py` (29/29 ПАСС) +
`scripts/tb_txclient.v`.

## Протокол

| Параметр | Значение |
|---|---|
| Окно | страница **F000h–F0FFh** (`localparam WIN_PAGE = 8'hF0`) |
| Триггер | запись в память (`IOM=0`, `WR#=0`) с адресом страницы |
| Пакет | **2 байта 8N1**: `[адрес A0–A7][данные]`; старший байт адреса = F0h — константа, ПК знает её |
| Бод | **1 923 077,8** (`BAUD_DIV = 13`: 25 МГц/13; бит ровно 520 нс) |
| Задержка вывода | ~11–13 мкс на запись (CPU заморожен только на голову пакета) |
| Потолок | ~77 тыс. записей/с (бэку-ту-бэк: пакет #2 встаёт в очередь на `hold_req` ещё при передаче #1 — потерь нет) |

## Как это работает (одна запись в окно)

```
T1 (ALE=1): декод win_hit = !IOM && {A15..A8}==F0h  ->  hold_req=1 -> HOLD(P81)
            (HOLD стабилен задолго до T2 -> ВМ85А сэмплирует его в T2 ЭТОГО ЖЕ
             цикла, HLDA - в конце его же; addr_latch/bus_reg не перезаписать)
T2:         данные записи -> bus_reg (штатный захват v3), WR# отработал
WB1..WB4:   writeback в ОЗУ КАК В v3.9.2 (запись не теряется и не дублируется)
HLDA:       CPU отпустил шину; FSM вернулась в IDLE ->
            пакет: [addr_latch][bus_reg], 20 бит, 10,4 мкс
2-й байт:   в момент его загрузки в shreg hold_req/tx_req СНИМАЮТСЯ - CPU
            работает, пока хвост пакета доезжает
```

Во время окна «CPU вне шины» (`tx_hold = hold_req | hlda_q`) выбор памяти
гасится жёстко (`CS_n`/`CSr_n` = 1): в HLDA процессор **флоатит** A15/IOM, и
живой декод выбирал бы ОЗУ/ПЗУ случайно. В WB выбор ОЗУ — по-прежнему от
FSM (п.16 базы). Заодно гейт закрывает окно «HOLD снят, HLDA ещё не упал».

HOLD берётся именно в **T1** цикла записи (а не по факту WR#): HOLD, поднятый
в T1, гарантированно сэмплируется ВМ85А в T2 этого же машинного цикла —
грант без промежуточных циклов, зафиксированный `addr_latch`/`bus_reg`
корректен всегда. Релиз — на загрузке 2-го байта: адрес и данные к этому
моменту уже в `shreg`, шина нужна только CPU.

## Почему в v1 было 2 байта (история вопроса о «4К»)

3-байтовый пакет (hi+lo+data) требует +8 триггеров под захват A8–A15: во
время HLDA наблюдатели AH8–AH14/A15 **флоат**, читать их на передаче нельзя.
От фита v3.9.2 это 85 − 3 (soft-UART) + 22 лог. МЦ txclient = ~104/108; плюс
8 МЦ под hi = 112 — **не лезет** в 108. Для страницы-окна старший байт и так
константа, поэтому 2 байта строго лучше (−10 бит-периодов на пакет).
**В v2 вывод пересмотрен**: hi-байт хранить негде и не нужно — он
сериализуется первым прямо с живых AH-пинов (см. раздел v2).

## Правила для прошивки (v1)

1. Окно **только ЗАПИСЫВАТЬ**: чтение из F0xx тоже замирает CPU на один
   цикл (пинг-понг HOLD-HLDA) — без пакета, просто ~1–2 мкс простоя.
2. Код из окна **не исполнять** (выборка команды — тот же «цикл чтения»).
3. Никаких портов не нужно; стек/переменные монитора (FFE8–FFF8) окно
   не задевает.

## Сторона ПК (v1)

Приёмник 1 923 077 8N1, кадры парами `[lo][data]`, страница F0 — константа.

# v3.10-порт: терминальный вывод через захват записи в порт 07h (сохранено)

**Статус:** RTL готов, верифицирован цикл-точной моделью (33/33 PASS, `sim_txclient.py` в корне).
Фит в ISE НЕ выполнялся (нет инструмента в песочнице) — чек-лист фита и план Б ниже.
База: **v3.9.2** — всё, кроме TX-тракта, бит-в-бит v3.9.2.

## Идея

Передатчик пишет **только то, что процессор пишет в область вывода**. CPLD ловит
запись в порт **07h** и пересылает байт в CH340G своим UART. Адрес на провод не
выносится — ПК знает, что весь поток = вывод терминала. SOD-транзит (CPU
бит-бэнжал SOD → CPLD → CH340, v3.7) удалён; приём (CH340 → CPLD → SID, RIM 20h)
не тронут. **Вопрос владельца «зачем порт 07h» закрыт**: это был триггер v3.10;
в оконной/логгерной схеме порты не нужны вовсе (04h–07h в v3.9.2 — резерв от
удалённого UART, Task 69).

## Протокол

| Операция | Смысл |
|---|---|
| `OUT 07h, A` | символ в терминал ПК (UART 115200 8N1, нога P39 → CH340G.RXD) |
| `IN 07h` | бит 0 = **TXRDY** (1 = окно приёма открыто, запись будет принята); биты 7–1 = 0 |
| `OUT 00h/01h/02h`, `IN 03h` | без изменений (сегменты / разряды+SND / колонки / KBROW) |
| `OUT 04h…06h` | резерв, как в v3.9.2 |

- Декод порта — по **A2–A0** (стиль проекта): алиасы `0Fh, 17h, …` тоже работают.
- Кадр: старт + 8 бит (LSB first) + стоп; **бит = 217 тиков 25 МГц = 8,68 мкс =
  115207,4 бода (+0,006 % к 115200; CH340G на 115200 точен)**.
- `RCONST` — параметр модуля `serial_tx` (216 по умолчанию).

## Контракт прошивки

```asm
; putchar: символ в C — без потерь, темп до ~12,5 тыс. знаков/с
PUTC:   IN    A,(07h)     ; 10T
        RRC               ;  4T   ; бит 0 -> CY
        JC    PUTC_OK     ; 10T/7T
        JP    PUTC        ; ожидание (период опроса 21T = 5,9 мкс)
PUTC_OK:MOV   A,C
        OUT   (07h),A
```

- **Пишешь без опроса — байты теряются** (окно закрыто → строб игнорируется).
  Это документированное поведение, а не дефект.
- TXRDY=1 гарантирует приём: писатель один (CPU), окно непрерывно до загрузки.

## Безопасность по построению (+2 МЦ к голой схеме uart.v)

Маркер `busy` в uart.v падает **на старте бита b7** — перезагрузка, попав в первые
50 % бита b7, портила бы ещё не отобранный приёмником бит (запас съедает
квантование CH340 ±0,2 %). В v3.10 окно приёма

```
tx_acc = !busy & !stop_q & !busy_d          (TXRDY = tx_acc)
stop_q: set — падение busy (начался b7); clear — bittick через бит (начался стоп)
```

открывается **только со старт-бита стопа** — перезагрузка физически не может
попасть в биты данных (худший случай — срезанный стоп = FE-флаг у ПК, байты
целы). Плюс 1-тактный строб `tx_send_q` вместо защёлкивания уровнем.

## Вердикт «холд vs буфер» (вопрос владельца)

Буфер: WR# к моменту захвата уже отработан, HOLD лишь придерживал бы следующий
доступ; холд = те же 21 МЦ + FSM HOLD/HLDA (+5..8) = 106..109/108 на грани
непомещения, с троттлингом CPU и касанием ноги 81 (PGND). Буфер с TXRDY-поллингом
даёт те же гарантии без потерь (период опроса 21T = 5,9 мкс < бит 8,68 мкс).
**В v1/v2 вердикт пересмотрен**: там HOLD несёт другую функцию — не защита
захвата (адрес/данные и так защёлкнуты FSM), а удержание шины, пока пакет не
загружен в shreg; в v2 — ещё и гарантия валидности трёх источников пакета
(hi/lo/data) до конца передачи (см. раздел v2).
